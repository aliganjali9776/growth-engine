# Build 4F — Strategy Executive Dashboard

Growth Engine by 1 Minute Manager · 2026-09-23

## Completion report

1. **Architecture.** `/strategy/dashboard`, `/strategy/reports`, and `/strategy/reports/executive` share a read-only view component and pure selectors in `lib/strategy/dashboard`. Existing StrategyProvider owns storage. No aggregate cache, new storage key, sample history, or independent dashboard dataset is written. `/strategy/report` redirects to the reporting center. The selected cycle is carried to the report/presentation links in the URL.
2. **Health formula.** Version 4F.1 uses pacing 35%, confidence 20%, evaluated initiative effectiveness 20%, review discipline 15%, and alignment 10%. Existing Objective health already incorporates KR status, confidence and completeness, so it is shown as explanatory evidence with zero additional weight. Counting Objective health, KR status and confidence independently would count the same risk repeatedly. Pacing uses `100 − max(0, expected time progress − actual progress)` per KR, weighted inside each Objective, then averages known active Objectives equally. Confidence is the mean of known active KR confidence ×10. Effectiveness scores effective=100, promising=75, weak=35, ineffective=0; notEvaluated is excluded. Discipline averages due weekly coverage and 30-day Adapt coverage. Alignment averages applicable relationship/ownership coverage groups. Known weights are renormalized; health requires at least 60% available base weight and calculable pacing. These are explained management heuristics, not calibrated probabilities.
3. **Transparency.** Expandable breakdown shows every component, score, base weight, normalized contribution, availability and rationale. It shows coverage, pre-cap and final scores. Critical risk caps health at 39, high at 59, and medium risk or incomplete evidence at 74. Final integer bands: 0–39 critical, 40–59 off track, 60–74 attention, 75–89 on track, 90–100 strong. Missing confidence/effectiveness is never scored as zero. Partial Objective coverage is displayed independently.
4. **Risk engine.** Typed findings include stable id, category, severity, affected entity IDs, evidence, management action, destination and ranking rationale. Severity dominates the ranking; weight ≥20%, deadline proximity, first strategic priority, confidence ≤3, stalled duration and repeated blockers add explicit tie-breaks. Initiative priority determines blocked-risk severity. Sources include canonical KR/Objective risk, stale/stalled data, confidence decline, recurring blockers, effectiveness, overdue initiatives, capacity warnings, alignment/ownership gaps, review discipline and recent changes. Findings are independent evidence and may reference the same entity; they are not a count of unique failing Objectives.
5. **Management focus.** Highest-ranked finding is selected deterministically and linked to its decision context. The summary uses actual progress, health, known confidence and that finding. No generated advice service or AI is called.
6. **Objective reporting.** Compact rows show priority, owner, lifecycle, canonical weighted progress, canonical health, confidence, KR status mix, execution, execution–result gap, deadline and stored micro-trend. Missing or skipped weeks are not joined with a fabricated line.
7. **KR reporting.** Active-Objective counters show achieved/on-track/at-risk/off-track/not-started/unknown and freshness. Simple KR mean is distinguished from the equal mean of valid weighted Objective progress. The risk-ordered detail table includes owner, weight, current/target, actual, expected time progress, gap, confidence, status and last observation. Rows can also show draft Objective KRs; active counters are explicitly labelled. Expected progress is a comparison baseline, not a forecast.
8. **Weekly trends.** Default window is the last 13 cycle weeks ending at the latest recorded snapshot; 26/all ranges are available. Only completed-review snapshots appear. Missing weeks and null measurements remain gaps. Progress/confidence switch, accessible week details and links expose stored values. Dated target/priority/initiative changes and completed Adapt reviews have event markers and linked explanations. Momentum reuses Build 4D's explained directional comparison and stays insufficient without enough evidence.
9. **Confidence.** Mean and four compact distribution bars (1–3, 4–6, 7–8, 9–10), low-confidence KR links and largest declines across three consecutive completed reviews. Unrecorded confidence is not assigned to a distribution bucket.
10. **Execution versus result.** Paired bars use existing execution selectors and KR-derived result progress. They show signed gaps and the canonical cautious interpretation. No claim that the initiative caused the result; a scatter matrix was unnecessary for readability.
11. **Initiatives.** Portfolio counters and a linked table show progress, effectiveness, expected/actual impact text, status and owner. Canonical initiative/KR signals identify high execution with weak result movement. Completed-but-weak and completed-but-unevaluated are distinct. Incompatible impact units are not numerically aggregated.
12. **Blockers.** Latest completed KR check-in and currently blocked initiatives supply the list. Consecutive normalized recurrence is counted; the latest blank blocker clears the old finding. Owner, entity, last evidence date, recurrence and current evidence status are visible. Exact normalized text matching deliberately does not infer semantic similarity between differently worded blockers.
13. **Changes.** Dated audit entries show field, before/after values, reason and source review. Counters separate target, deadline, initiative and priority changes. Weekly/Adapt decisions and resource shifts are presented alongside them. Cycle-close events link to the cycle learning/review page. High change count alone is a low-severity descriptive signal, not proof of bad strategy.
14. **Alignment.** Expandable direction → priority → Objective → KR → initiative hierarchy and five coverage groups. Reports filter by priority/Objective. Missing links, selected priorities without Objectives, Objectives without KRs, orphan initiatives and owner gaps are surfaced. Low-confidence unachieved KRs without initiatives prompt consideration, but no initiative is mandatory for every KR.
15. **Review discipline.** Due weekly completion, average stored review quality, last weekly/Adapt dates, due Adapt completion and cycle-review readiness are separated from outcome progress. Monthly due counts use 30-day periods, not a forecast or automatic review creation.
16. **Learning.** Current-cycle lessons, assumption supported/weakening/invalidated counts, stalled results, repeated blockers, confidence declines, initiative changes and resource shifts come from Build 4E. Historical lessons/assumptions/roles come from the final evidence snapshot when available.
17. **Completeness.** Separate coverage of Objectives with KRs, KR definition quality, measurable values, confidence, ownership, initiative links, current-week check-ins and completed history. Non-applicable groups remain unknown rather than an invented zero. The total is the mean of available groups, with each group shown so partial coverage is not hidden.
18. **Freshness.** This-week observation count, never-updated KRs, observations older than seven days and overdue weekly/Adapt reviews. Freshness is independent of completeness and progress. It concerns KRs of active Objectives; draft-cycle measurements can appear in detail without implying active review obligations.
19. **Reporting center.** Ten focused reports: Objectives, KRs, weekly trend, confidence, initiative effectiveness, execution/result, alignment, blockers, changes and learning. Cycle and applicable Objective/priority/owner/KR-status/initiative-status filters are available, plus trend range. Summary figures remain explicitly cycle-wide while filters narrow report rows. Pure serializable derived data provides the export foundation; no PDF/Excel library or export workflow was added.
20. **Executive presentation.** Dedicated route combines the header, focus, risks, Objective health, trend, execution/result and decisions. Print styles hide the application chrome and remove the sidebar margin. No PDF renderer was introduced; pagination across printers is not claimed as a separately certified PDF export.
21. **Visual decisions.** Restrained navy/gold/neutral palette, Vazirmatn RTL, one dominant executive header, numbered attention list, compact rows, text-labelled semantic statuses and progressive disclosure. The normal Strategy masthead is compact only on dashboard/report pages. No pie charts, decorative visualizations or wall of equal-weight cards.
22. **Responsive QA.** Browser checks at 1440×1000, 1280×900, 820×1180 and 390×844. Desktop header/focus, tablet Objective rows/trend and mobile summary/attention were visually inspected. Tables and charts scroll within their own regions; document width matched viewport width in checked 1280, tablet and mobile states. The original 127.0.0.1 data was not mutated; QA reused existing localhost records.
23. **Performance.** Generated fixtures exist only in tests: 10 Objectives/40 KRs/60 initiatives/13 weeks and 25/100/150/26 weeks. Five full-selector runs are timed with snapshot/check-in histories. Observed post-implementation runs were roughly 34–41 ms and 61–115 ms respectively; timing varies under concurrent build load. Tests enforce completion below 2 seconds, expected counts, 13-week selection and input immutability. Browser load testing did not inject those synthetic fixtures into user storage.
24. **Tests.** 322 passing tests: all 299 existing tests plus 23 Build 4F tests. Coverage includes canonical progress, health weight/availability/caps, missing confidence, no-history state, weighted KR risk, confidence decline, blocker recurrence/resolution, execution gap, effectiveness distinctions, alignment, completeness/freshness, frozen historical data, snapshot-only trend, dated events/range gaps, changes, focus/summary, no aggregate mutation, cycle filters and both performance fixtures. Historical test setup initially omitted the actual review→closed lifecycle and was corrected to exercise the real close operation.
25. **Production build.** TypeScript and optimized Next production build passed. Local production server starts on port 3000. Browser verification covers active, completed and draft/no-history cycles; health explanation, all ten report choices, risk/status/owner filters, report/presentation cycle handoff and KR/weekly-review drill-downs.
26. **Dependencies.** None added. Existing React/Next, TypeScript, CSS and SVG suffice. npm scripts append the dashboard test file; existing test suites remain enabled.
27. **Issues resolved / limits.** Fixed cycle-week boundary access, snapshot identifier use, a missing route in the freshness link, closed-cycle metadata precedence, report-cycle handoff, raw status/direction display, nested main markup, masthead density and mini-trend gap joining. Historical core uses the final Build 4E snapshot; weekly snapshots and audit/review collections use the existing protected immutable history. Legacy closed cycles without a final snapshot explicitly say they use the closed records. No synthetic history is created to fill gaps. Storage remains local-browser only.
28. **Before Strategy v1 sign-off.** Run acceptance sessions with real managers, agree on the heuristic health weights/caps and capacity limits, validate review cadence against the organization's calendar, and complete a dedicated keyboard/screen-reader/print acceptance pass. Production multi-user identity, server persistence/backup and permissions need a separate approved scope. Forecasting, AI, notifications, email, billing and BI integration remain intentionally outside Build 4F. Full cross-cycle analytics and export rendering are also deferred; the cycle-specific snapshot selectors allow later extension.
